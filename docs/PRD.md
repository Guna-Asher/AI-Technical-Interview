# Product Requirements Document (PRD)

## AI-Powered Role-Based Candid Screening System

**Version:** 1.0  
**Purpose:** AI/ML & Backend Engineering Internship Assignment  
**Development approach:** Simple, Docker-first application built in small, verifiable phases

---

## 1. Product overview

Build a web application that conducts a personalized technical interview based on a candidate's resume, selected job role, and a technical knowledge base.

The candidate uploads a resume, enters a target role, answers interview questions generated by an LLM using relevant retrieved material, and receives a saved summary of the session.

The main goal is to demonstrate a complete working AI application, including frontend/backend integration, a RAG pipeline, API design, and persistent data storage. This is an internship assignment and portfolio project, not a production recruitment platform.

## 2. Problem and goal

Fixed interview-question lists do not necessarily reflect a candidate's background. This application should generate questions that are meaningfully influenced by:

1. The candidate's resume and extracted skills.
2. The selected job role.
3. Relevant passages retrieved from a technical knowledge base.

The application must demonstrate the complete flow from resume upload to final interview summary. Questions should be grounded in retrieved source material rather than generated from a generic prompt alone.

## 3. Scope

### Required for the initial working product

- Upload a resume in PDF or plain-text format.
- Enter the job role to be interviewed for.
- Extract relevant skills, technologies, and experience from the resume.
- Ingest technical book material into a searchable knowledge base.
- Retrieve relevant knowledge using embeddings and Chroma.
- Generate role- and resume-informed interview questions through OpenRouter.
- Conduct a text-based interview through the frontend.
- Save the session, questions, and candidate answers in PostgreSQL.
- Display a final summary with basic insights about the interview.
- Run the application through Docker Compose.
- Include a README, relevant tests, and a demo video.

### Out of scope for the initial version

- Authentication and user accounts.
- Recruiter or administrator dashboards.
- Voice or video interviews.
- Adaptive follow-up questions based on every previous response.
- Complex scoring or claims that the report predicts real-world job performance.
- Microservices, Kubernetes, Redis, background queues, or agent frameworks.
- Production-scale deployment and advanced observability.

Build the required workflow first. Optional enhancements must not delay a complete end-to-end demonstration.

### Dynamic behaviour requirement

Interview content and workflow must be generated at runtime from real inputs: the role and resume-derived profile supplied by the candidate, passages retrieved at runtime from the indexed knowledge base, and responses from the configured OpenRouter model. Answer evaluation and reports must be derived from the candidate's actual responses.

The application must not ship or fall back to hardcoded job-role lists, predefined questions, canned answers, fixed evaluations, fabricated reports, or hardcoded retrieval results, and must not restrict interviews to a predefined set of roles. A role is validated as user input only. Knowledge coverage for a role is determined by actual retrieval results, and insufficient coverage must be reported honestly.

Structural rules (database schema, constraints, status values, input validation) and configuration (environment variables, model identifier, question count, chunking parameters) are allowed; they are not interview content. Test fixtures may use synthetic values, but these must never become default runtime content.

## 4. Users and primary workflow

The primary user is a candidate who wants to practise a technical interview for a selected role.

1. **Upload resume:** The candidate uploads a PDF or TXT file.
2. **Enter role:** The candidate enters the job role they want to practise for.
3. **Process resume:** The backend extracts resume text and builds a structured profile of relevant skills and experience.
4. **Retrieve knowledge:** The backend builds a query from the role and candidate profile, then retrieves relevant passages from Chroma.
5. **Generate questions:** OpenRouter generates a manageable set of interview questions using the candidate profile and retrieved passages.
6. **Answer questions:** The candidate answers through the Next.js interface. The session tracks progress and saves submitted answers.
7. **View summary:** The system displays and saves a final summary, including the questions asked, answers given, and basic observations or improvement suggestions.

Use five questions by default, with the number configurable. Adaptive follow-up questions are optional.

## 5. Technology decisions

These are the agreed implementation choices for this project.

| Area | Technology | Purpose |
|---|---|---|
| Frontend | Next.js, React, TypeScript, Tailwind CSS | Resume upload, role entry, interview UI, and results |
| Backend | Python + FastAPI | API endpoints, application logic, and AI/RAG orchestration |
| Application database | PostgreSQL | Sessions, questions, answers, and reports |
| Database access | SQLAlchemy | Database queries and model mapping |
| Migrations | Alembic | Manage database schema changes |
| Document parsing | PyMuPDF | Extract text from PDF resumes and knowledge documents |
| Embeddings | Sentence Transformers, `all-MiniLM-L6-v2` | Generate embeddings locally inside the backend container |
| Vector database | Chroma | Store and retrieve knowledge chunks by semantic similarity |
| LLM provider | OpenRouter API | Generate interview questions and the final summary |
| Backend tests | Pytest | Test core logic and API behaviour |
| Frontend tests | Vitest and React Testing Library where useful | Test important frontend behaviour |
| Runtime | Docker + Docker Compose | Run and connect the application services |

Do not add technologies without a clear need. Choose compatible, supported versions and verify the configuration used by the project.

## 6. Application architecture

Use a simple modular monolith. The frontend and backend are separate applications, but backend business logic stays in one FastAPI service.

- **Next.js frontend:** Calls FastAPI over HTTP. It does not connect directly to PostgreSQL, Chroma, or OpenRouter.
- **FastAPI backend:** Coordinates resume processing, retrieval, question generation, interview sessions, and reports.
- **PostgreSQL:** The source of truth for application records.
- **Chroma:** Stores document chunks, embeddings, and source metadata for semantic retrieval.
- **Sentence Transformers:** Runs in the backend container to create query and document embeddings.
- **OpenRouter:** External HTTPS service used for LLM generation. It is not a Docker service.

PostgreSQL and Chroma have different responsibilities and must not be treated as interchangeable.

### Docker services

The root `compose.yaml` should run these services:

- `frontend`
- `backend`
- `postgres`
- `chroma`

Use named Docker volumes for PostgreSQL data, Chroma data, and the downloaded embedding-model cache. Configure environment variables, useful health checks, and service dependencies. Avoid relying on fixed startup timing.

The application should start with:

```bash
docker compose up --build
```

The developer should not need to install Node.js, Python, PostgreSQL, or Chroma directly on the host. Docker and Docker Compose are the runtime prerequisites. The browser must use a browser-accessible backend URL such as `http://localhost:8000`; Docker service names such as `backend` are for container-to-container communication.

## 7. Functional requirements

### FR-1: Resume upload and parsing

- Accept PDF and plain-text resumes.
- Validate supported file types and set a reasonable maximum upload size.
- Extract the text and handle empty or unreadable files with a clear error.
- Produce a structured candidate profile containing relevant skills, technologies, and experience.
- Do not retain the original resume file longer than necessary for processing.

### FR-2: Role input

- Let the candidate enter the target role as free text in the frontend; do not restrict it to a predefined list.
- Validate the role only as user input (non-empty, reasonable length).
- Determine knowledge coverage for the role at runtime from actual retrieval results against the indexed knowledge base.
- Report insufficient coverage honestly; do not claim a role is grounded in the source material when retrieval returns little relevant content.

### FR-3: Knowledge ingestion

The provided assignment identifies machine-learning and data-science books as the primary RAG resources. Use those provided resources as the knowledge base rather than replacing retrieval with generic internet search.

The ingestion command must:

1. Extract text from selected PDF documents.
2. Split text into reasonably sized, overlapping chunks.
3. Preserve the document title and page or chunk metadata where available.
4. Generate embeddings using `all-MiniLM-L6-v2`.
5. Store the chunks, embeddings, and metadata in Chroma.
6. Be repeatable without uncontrolled duplication of already-ingested chunks.

Ingestion must be a separate command run inside the backend container. Do not re-ingest all documents on every interview request.

Start with one appropriate book. Expand only after ingestion and retrieval work correctly. Do not claim a role is grounded in the knowledge base unless retrieval returns relevant material for it.

### FR-4: Retrieval and question generation

- Construct retrieval queries using the selected role and relevant resume information.
- Retrieve relevant content from Chroma using embeddings.
- Pass the retrieved passages and candidate profile to OpenRouter.
- Generate questions that test relevant conceptual or applied understanding.
- Avoid relying solely on fixed templates or generic questions.
- Store each question with references to the chunks that informed it, including source details where available.
- Validate the generated output before saving it.
- Handle an empty or clearly irrelevant retrieval result honestly rather than claiming the resulting question is source-grounded.

Use a configurable OpenRouter model. Required environment variables include:

- `OPENROUTER_API_KEY`
- `OPENROUTER_MODEL`

The API key must remain server-side and must never be exposed to the browser or committed to source control. Handle common timeouts, rate limits, provider failures, and invalid responses without losing already-saved interview data.

### FR-5: Interview session

- Create a session linked to the selected role and candidate profile.
- Present questions in a clear order.
- Accept text answers and associate each answer with its question and session.
- Show interview progress and clear loading/error states.
- Preserve saved progress across a browser refresh when the session identifier is available.
- Prevent a failed request from silently discarding an answer.

### FR-6: Final summary

At the end of the interview, generate and save a structured summary containing:

- Session details and selected role.
- Questions asked and answers submitted.
- A concise overall summary.
- Basic observations about demonstrated strengths and topics that may need more practice.
- Practical recommendations for further study.

The report may use OpenRouter to summarise the saved interaction. Present AI feedback as guidance, not as a definitive or calibrated judgement of a candidate's professional ability.

Detailed answer scoring and adaptive interviews are optional unless time remains after the required workflow is complete.

## 8. Application data

PostgreSQL should store the application data needed to reproduce and display an interview.

The initial data model should cover:

- **Interview session:** Identifier, selected role, structured candidate profile, status, and timestamps.
- **Question:** Session relationship, order, question text, topic or difficulty where useful, source-chunk references, and timestamp.
- **Answer:** Question relationship, submitted text, and timestamp.
- **Interview report:** Session relationship, generated summary, strengths, improvement topics, recommendations, and timestamp.

Use appropriate identifiers, foreign keys, constraints, and timestamps without adding unnecessary tables. Use SQLAlchemy and Alembic. Raw resume storage is not required for the first version; retain the extracted profile needed for the session instead.

Chroma should store knowledge chunks, embeddings, document identifiers, source titles, and page or chunk metadata where available.

## 9. Backend and frontend expectations

### Backend

Use Pydantic schemas for API requests and responses, managed SQLAlchemy sessions, and straightforward service functions. Keep API routing, configuration, data access, resume parsing, ingestion/retrieval, and OpenRouter interaction in clear modules as those responsibilities are implemented.

The API should support the core lifecycle: create a session, start or retrieve its questions, submit answers, complete an interview, and retrieve its report. Exact endpoint names can be chosen during implementation as long as the lifecycle is clear and consistently validated.

Provide a health endpoint that verifies the backend is running and, where appropriate, that PostgreSQL is reachable.

### Frontend

Provide these main screens or states:

- Resume upload and role entry.
- Interview in progress, including the current question, answer input, and progress.
- Final results and report.

Keep the UI clear and usable. A complete workflow and correct data handling matter more than elaborate visual effects.

## 10. Configuration, security, and errors

- Provide a `.env.example` with placeholder values and document required settings.
- Keep `.env` and real credentials out of version control.
- Never expose OpenRouter credentials to the frontend.
- Validate uploaded file type and size.
- Avoid unsafe or unnecessary permanent storage of resumes.
- Validate generated content before saving it.
- Return useful error messages without exposing secrets or internal stack traces.
- Preserve saved session data when a later AI request fails.
- Use persistent volumes so data survives normal container restarts.

Keep safeguards appropriate to an internship project. Do not build an elaborate authentication, compliance, or production-hardening system that is outside the assignment's scope.

## 11. Testing and acceptance criteria

Test important behaviour rather than every trivial implementation detail.

Minimum checks should cover:

- Resume parsing and invalid/empty document handling.
- Document chunking and source metadata.
- Chroma ingestion and retrieval.
- Question output validation and source references.
- Core API validation and interview session transitions.
- PostgreSQL persistence of sessions, questions, answers, and reports.
- Handling of OpenRouter errors, using mocked responses for ordinary tests.
- Frontend build and important interview interactions.

### Definition of done

The project is complete when:

1. The application starts through Docker Compose using the documented configuration.
2. A candidate can upload a supported resume and enter a target role.
3. The backend extracts candidate information.
4. Technical source documents can be ingested into Chroma through a container command.
5. The application retrieves relevant passages and generates questions through OpenRouter.
6. Questions retain traceable references to retrieved chunks.
7. The candidate can answer questions through the frontend.
8. Sessions, questions, answers, and the final report are saved in PostgreSQL.
9. The report is available in the frontend.
10. Main paths and common errors are tested, and the README explains setup, ingestion, testing, and design decisions.
11. A demo video shows the full workflow working end to end.

Do not claim a check passed unless it was actually run and passed. If Docker, external credentials, or source documents are unavailable, state what could not be verified.

## 12. Development phases

Implement the product in small phases and review the results after each one.

1. **Foundation:** Repository structure, Docker Compose, Next.js, FastAPI, PostgreSQL, Chroma, configuration, and health checks.
2. **Persistence:** SQLAlchemy models, Alembic migrations, and core interview data operations.
3. **RAG:** Document ingestion, chunking, local embeddings, Chroma storage, and retrieval.
4. **Resume and LLM:** Resume profile extraction, OpenRouter integration, and contextual question generation.
5. **Interview flow:** Connect the frontend to the backend; collect and persist answers.
6. **Summary and delivery:** Generate the final report, add focused tests, document setup, verify the full flow, and record the demo.

For each phase, inspect the current repository, plan only the requested phase, implement it, run relevant checks, and report actual results. Do not implement future phases without approval. Fix meaningful blockers, but do not let minor edge cases or optional features derail progress.

The internship assignment requires:

- A complete, clean GitHub repository.
- A README with setup instructions, architecture, and key design decisions.
- A mandatory demo video showing the complete end-to-end system and how its components interact.

The assignment specifies a 48-hour window from receipt. Prioritise the working core workflow and required deliverables over optional enhancements.
